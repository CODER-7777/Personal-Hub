## How the new sync works, and its limits

Local edits update the UI immediately and enter `personal-hub-outbox:{uid}` in localStorage. On reconnect the app runs a Firebase transaction against that collection, merging additions/deletions and changed fields into current cloud data. Cloud echoes are applied with pending local operations overlaid. Queue entries are removed after acknowledgement. A first login on a device waits for account hydration; an already cached account can resume offline.

This addresses the central lost-record bug: Firebase `set()` replaces data at its path, whereas transactions can retry against concurrent updates. See [Firebase read/write documentation](https://firebase.google.com/docs/database/web/read-and-write).

The solution has practical limits:

- Concurrent edits to **different fields** merge. Concurrent edits to the **same field** use the last committed value; there is no conflict dialog or collaborative text merge.
- Goal progress is still an absolute count. Two devices incrementing the same goal can lose one increment. Model increments as operations or events in a future schema.
- Habit completion dates merge as set changes. Lists remain Firebase arrays for compatibility; transactions still cover an entire collection. A future `items/{id}` schema would reduce contention and transferred data.
- A crash after a cloud commit but before local acknowledgement can replay an operation. Additions, deletions and field patches are designed to be idempotent, but this is not an exactly-once service.
- localStorage/outboxes are plaintext and depend on available disk/browser storage. Clearing app data removes unsynced work. Storage failures are displayed; keep the app open until work syncs or export it.
- Older releases still write whole arrays. They can undo improvements made by this client. Update every active client before relying on multi-device editing.
- Firebase Auth `displayName` is set at signup; subsequent Settings edits update the Hub database profile. Features integrating directly with Auth metadata would need additional synchronization.

Old caches with no recorded owner are preserved in `personal-hub-legacy-recovery`, excluding the Gemini key, and are **not** uploaded automatically into the next signed-in account. If old offline records appear missing, preserve/export that localStorage JSON through browser/Electron developer tools before clearing storage. This recovery currently has no guided import UI; verify the original account and review records before any manual restoration.

### Safe rollout and diagnosing a sync problem

1. Export a backup from every device containing valuable local work. Preserve any legacy-recovery/outbox entries before uninstalling or clearing storage.
2. Build and update web/PWA, Android and desktop clients together. Use the same Firebase project and sign-in account on each; equal display names do not establish account identity.
3. Check Settings → Account sync. A pending count means writes remain local. Retry after reconnecting; capture errors rather than repeatedly clearing storage.
4. Check deployed Firebase rules when reads/writes fail. The checked-in `database.rules.json` restricts access to `$uid === auth.uid`, but production deployment was not inspected or changed.
5. Verify two devices: edit different class fields, add different records, disconnect one device, edit/restart it, then reconnect. Confirm both edits and a zero pending count. Repeat logout/login with two accounts to check isolation.

## Remaining security concerns, ordered by priority

### 1. Native runtime and dependency upgrades remain necessary

Patched root `@capacitor/android`, `@capacitor/core` and `@capacitor/cli` from 8.3.1 to **8.5.2**, removing the Android origin/proxy advisory from the online npm audit. The upstream issue lets malicious remote content use the internal HTTP interceptor to gain the app origin. Existing APKs remain vulnerable until rebuilt and replaced. See [Capacitor's advisory](https://github.com/ionic-team/capacitor/security/advisories/GHSA-rvm3-566m-v7fv).

The remaining online dependency snapshot is in [dependency-audit.json](dependency-audit.json):

| Install tree | Low | Moderate | High | Critical | Total package entries |
| --- | ---: | ---: | ---: | ---: | ---: |
| Root | 3 | 8 | 17 | 2 | 30 |
| Electron | 1 | 4 | 27 | 1 | 33 |

These are vulnerable package entries, including dependency propagation and build tools; they are **not** 63 independently proven application exploits. Root critical entries include `proxy-addr` in the Express tree and `tar` in tooling. Express appears unused by the frontend. Trusted-source icon generation uses an older `sharp`; do not extend it into an untrusted upload service without upgrading.

Desktop still uses Electron 26 and electron-builder 23.6.0. Plan a supported Electron/Capacitor bridge and packager upgrade with native regression tests. Electron only supports its latest three stable major releases. The old builder is also below the fix for the NSIS unsafe DLL search-path advisory. See [Electron support policy](https://www.electronjs.org/docs/latest/tutorial/electron-timelines) and [electron-builder advisory](https://github.com/electron-userland/electron-builder/security/advisories/GHSA-r4pf-3v7r-hh55).

Do not blindly run `npm audit fix --force`: the audit suggests breaking changes/downgrades in places. Remove unused dependencies, upgrade direct packages deliberately and audit both installation trees again.

### 2. Desktop isolation is improved but incomplete

Renderer Node integration is disabled and context isolation remains enabled. Production script CSP no longer permits `unsafe-eval`; external URL handling is restricted. **`sandbox: false` remains** because the legacy Capacitor preload depends on Node modules. Migrate that preload/plugin bridge before enabling the sandbox. Test authentication, external links, native plugins and exports in the packaged application. ExcelJS currently emits an eval warning; its behavior under the stricter desktop CSP has not been verified. See [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security).

### 3. Data deletion, local storage and backend validation

- Delete Account currently deletes Firebase Auth only. Cloud `user_data/{uid}` remains. The UI/privacy copy now discloses this. Implement authenticated server-side cleanup, ideally with a deletion trigger or Firebase deletion extension, and cover retention/backups before promising complete erasure.
- Checked-in UID rules provide account isolation but no record schema/size validation. Add validation rules and emulator tests for unauthorized reads/writes and invalid records; assess App Check/rate limits. Client validation is bypassable.
- Offline cache/outbox contains notes, finances and profile data in plaintext. Android backup is now disabled, but this does not encrypt data or remove OS notifications. Choose an explicit shared-device policy and native secure storage/encryption if needed.
- A Firebase client API key is expected to be public; database rules authorize data access. Do not mistake hiding the Firebase configuration for fixing access controls. See [Firebase API key guidance](https://firebase.google.com/docs/projects/api-keys).

### 4. AI key handling and external services

Removed build-time Gemini key injection and persisted Gemini keys. Settings now holds a key only for the current app session, and logout clears it. This reduces persistent exposure but a browser-held key is still accessible to that client and any injected script. For managed AI, use an authenticated server endpoint with authorization, quotas and abuse controls. See [Google API key guidance](https://ai.google.dev/gemini-api/docs/api-key).

AI requests can send timetable/receipt images, schedule/task context or finance summaries to Google. Privacy copy describes this; add a preview/consent step at the relevant feature. External avatar URLs and proxy-backed requests also disclose network metadata to third parties.

## Design suggestions

Keep the black/lime identity, but make ordinary text easier to read. Many helper labels are 9–11px, uppercase and widely spaced. Use normal sentence case and 14–16px body text; reserve compact uppercase for short section labels.

On phones, show four primary bottom tabs plus More instead of compressing every module into the bottom bar. Use Today as the first view with the next class, due tasks and quick add. Group Settings into Account, Sync, Appearance, AI and Privacy. Keep at least 44px touch targets and explicit input labels.

Reduce the forced 3.5-second splash on repeat launches. Add undo for routine deletion, scanning previews before automatic imports and clear empty states. Connect or remove the dashboard search affordance so it behaves predictably.
